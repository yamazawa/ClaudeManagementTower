1. 目的とスコープ

確定 自宅PCでClaude Codeを実行し、Web UIからGitHub Issueに対応する開発タスクとサブタスクを管理する。外出先のスマホから指示を送信し、実行状況・作業結果・PRを確認できるようにする。

基本思想：「人間がタスク・サブタスクの目的を入力 → Claudeが自律判断して実装 → HTMLで判断と成果を報告 → 人間がPRをレビュー・マージ」。実行中の問い合わせを前提にしない。

MVPに含む

  • Issue一覧・詳細の取得と表示、Issueの進捗状態表示
  • Issue配下のサブタスク作成、専用ブランチ・Draft PR作成
  • サブタスク単位のClaude Code実行と履歴蓄積
  • 実行状態表示、結果HTMLレポート、PRリンク
  • Webサーバーとワーカーのプロセス分離、スマホからの認証付きアクセス

MVPから除外

  • 別Claudeセッションによる自動コードレビュー（後続）
  • 実行時間上限・API費用上限の設定UI（後続）
  • Claudeによるサブタスク自動分割、定期実行（後続）

2. 確定した業務ルール

単位ルール
タスク1タスク = 1 GitHub Issue。開発進捗はIssue側で管理・連動する。
サブタスク1サブタスク = 1 PR。専用ブランチを持つ。作業開始時はDraft PRを基本とする。
サブタスク完了対応PRがマージされた時点。Claudeの実装完了だけでは完了にならない。
Issue完了必要なサブタスクのPRがすべてマージされた後にIssueをクローズする。
修正PRマージ前のレビューNGは同じサブタスク・同じブランチ・同じPRで修正し、再レビューする。PRマージ後に問題が判明した場合のみ、新しい修正サブタスクとPRを作成する。
PRのIssue参照説明文は Related to #42 形式。Closes #42 は使わず、自動クローズを避ける。
Claudeの判断不明点は既存コード・仕様を調査し、合理的に補足して実装。原則ユーザーに質問しない。
報告Claudeが自分で判断した内容・理由をHTMLで報告。回答・ログはサブタスク履歴に蓄積する。
状態Issueの開発進捗と管理塔のClaude稼働状態を分離する。
技術的な要確認点：差分のない新規ブランチに対するDraft PR作成が、対象GitHub環境・APIで可能かを最初に実機検証する。不可の場合は黙って初期コミットを追加せず、エラーを明示して設計判断を求める。MVPに複雑なフォールバックは不要。

実装前の確認事項と停止条件（確定事項を尊重）

差分ゼロのDraft PRが作成できない場合は、該当サブタスクの開始を停止し、失敗理由を報告する。ダミーコミットの追加、PRを作らないままの実行、別ブランチへの切替えを自動で行わない。人間が代替フローを決定してから再開する。

レビューNGはマージ前に限り同じサブタスク・ブランチ・PRを再利用する。修正実行前には既存PRが未マージであることを再確認する。マージ済み・クローズ済みのPRには追記しない。

外出先スマホ / PC
    │ HTTPS + ログイン認証

自宅Windows PC
    ├─ Webサーバー（FastAPI）
    │    ├─ HTML/JavaScript 管理画面
    │    ├─ GitHub API連携
    │    └─ SQLite（タスクキュー・履歴・状態）
    │
    └─ Claude実行ワーカー（独立プロセス）
         ├─ キュー取得・排他制御
         ├─ Git worktree / ブランチ操作
         ├─ Claude Code CLI / Agent SDK
         ├─ テスト・コミット・push
         └─ HTMLレポート生成・保存

GitHub：Issue / Branch / Draft PR / Merge 状態

確定 Webサーバーと実行ワーカーは分離する。ブラウザを閉じてもワーカーは継続する。

確定 Python + FastAPI、SQLite、シンプルなHTML/CSS/JavaScriptを採用する。MVPの画面状態更新は3秒間隔のポーリングとする。Git操作はGit CLI、GitHub操作は`gh` CLI（サブプロセス実行）を使用する。WebSocketはMVPでは採用せず、将来の拡張候補とする。

確定 GitHubホスティングはgithub.com（SaaS）とする。GitHub Enterprise Server等のセルフホストはMVPの対象外とする。

確定 GitHub認証は`gh auth login`済みの既存OAuthセッションを使い回す。ワーカー専用のPersonal Access Tokenは発行しない。このトークンはscope repo（アクセス可能な全リポジトリ）を持つため、対象リポジトリ限定の最小権限はトークン自体では実現されず、アプリ側の許可リスト判定に委ねる。

確定 Windows上で稼働させ、PowerShellおよびWindowsパスを考慮する。Claude Codeの実行にはインストール済みCLIの非対話モードまたは公式SDKを使用し、実装時に現行仕様を調査して選定する。MVPから設定可能なN個の独立ワーカーで最大N件を同時実行する。初期設定はN=3とする。

【確定・MVP】ワーカー数Nは設定で変更可能とし、ワーカー1個につきClaude Code実行を最大1件担当する。異なるサブタスクは最大N件並列実行できる。同一サブタスクは同時実行しない。各サブタスクに専用Git worktreeを割り当てる。

ORM・構成上の補足

SQLiteアクセスにはSQLAlchemy ORMを採用する。ワーカーのジョブ取得と同一サブタスク排他は、ORMの通常の読み書きだけに頼らず、SQLiteの原子的な更新とトランザクションで保証する。

Webサーバーとワーカーは別プロセスとし、HTTPリクエストの処理中にClaude Codeを直接起動して待機しない。

5. サブタスク実行フロー

Issue選択→サブタスク作成→ブランチ作成→Draft PR作成→Claude実行→HTML報告→レビュー→PRマージ
  1. GitHub Issueを選択し、タイトル・ClaudeへのINPUTを登録する。
  2. mainなど対象ブランチからサブタスク専用ブランチを作成・pushする。
  3. Issueへの参照 Related to #番号 を含むDraft PRを作成する。
  4. 作成に成功したらワーカーへ実行要求を登録。Claudeは対応worktree内で作業する。
  5. Claudeがコード調査・実装・テスト・修正を実行し、必要な変更をコミット・pushする。
  6. 作業結果・自律判断・未解決事項・テスト結果をHTMLレポートにまとめ、サブタスク履歴へ保存する。
  7. 実装成功時にDraftを解除し、PRをレビュー中にする（GitHub API操作）。
  8. 人間がGitHubでマージしたら、同期によりサブタスク完了にする。
  9. レビューNGの場合は同じサブタスクへ追加指示を投入し、同一worktree・ブランチ・PRで修正と再レビューを繰り返す。マージ後に発見した不具合のみ新しいサブタスクとして起票する。

実装提案 PRの作成・マージ状態はGitHub APIから取得。初期は定期ポーリングと画面上の「同期」操作でよい。GitHubのWebhook受信はMVPでは不要。

レビューで問題があった場合

確定 マージ前のレビューNG：既存サブタスクに追加指示を登録し、同じ作業ブランチ・同じPRでClaudeが修正する。修正内容を既存履歴へ追記し、同じPRを再レビューする。レビューNGを理由に新しいPRは作成しない。
確定 マージ後に問題が発覚：元のPRとサブタスクはマージ済・完了のまま維持し、新しい修正サブタスクと新しいPRを作成する。

タイミング処理サブタスク完了判定
Claude実装完了・PR未マージレビュー待ち未完了
レビューNG・PR未マージ同一PRへ追加コミットして再レビュー（何度でも可）未完了
レビューOK・PRマージGitHubのマージ状態を同期完了
PRマージ後に不具合発覚別サブタスク・別PRを新規作成元サブタスクは完了のまま

レビューNG時の再実行手順

追加指示を既存サブタスクの履歴に保存し、既存worktree・ブランチ・PRを対象に新たなexecution_jobを登録する。ワーカーは前回の実装とレビュー指摘を確認し、修正・テスト・コミット・push・HTMLレポート作成を行う。

レビューNGでの再実行時は必要に応じてPRをDraftに戻し、修正と検証が成功した後にDraftを解除する。失敗時はレビュー可能と誤認させない状態・エラーを表示する。

6. 状態管理

分類状態候補正式な情報源
Issue進捗未着手／設計中／実装中／レビュー中／マージ済（ラベル名は設定可能）GitHub Issue・ラベル
サブタスク/PR準備中／Draft／レビュー中／マージ済／クローズ（未マージ）GitHub PR + 管理塔
Claude実行待機中／キュー待ち／実行中／成功／失敗／中断管理塔 SQLite

不変条件： Claudeが成功してもPR未マージならサブタスクは完了ではない。PRマージ済みならサブタスクは完了。Issueクローズは全必要サブタスクのマージ確認後に人間または明示的な操作で行う。

実装提案 PRがマージされずクローズされた場合は「中止」として扱い、「完了」にしない。Issueのラベル運用は既存リポジトリのルールに合わせ設定可能にする。

7. データモデル（SQLite案）

実装提案 GitHubのIssue・PRそのものを重複して正本管理しない。外部IDと管理塔固有の実行・履歴データを保存する。

projects
  id, name, github_repo, repo_path, default_branch, created_at

tasks_cache
  id, project_id, github_issue_number, title, state_label, synced_at

subtasks
  id, project_id, github_issue_number, title, instruction,
  branch_name, github_pr_number NULL, lifecycle_state,
  created_at, updated_at

execution_jobs
  id, subtask_id, status, queued_at, started_at, ended_at,
  exit_code NULL, claude_session_id NULL, error_message NULL,
  worker_id NULL, claimed_at NULL, heartbeat_at NULL

execution_events
  id, job_id, sequence_no, event_type, content, created_at

reports
  id, job_id, html_path, summary, created_at

workers
  id, process_identifier, state, heartbeat_at, current_job_id NULL

複数回の追加指示は execution_jobs を追加し、過去の実行・回答を消さない。execution_events に指示、Claude出力、実行ログ、判断メモ等を時系列保存する。

DB制約例：UNIQUE(project_id, github_issue_number, branch_name)、PR IDの一意性、同一サブタスクに同時実行ジョブを作らない排他制御。

【確定・MVP】ジョブ取得はSQLiteトランザクションで原子的に行い、二重取得を防止する。ジョブ実行中はDBトランザクションを保持しない。SQLiteのWALモード、短い書き込みトランザクション、busy_timeoutを使用する。

排他制御・履歴保持の実装条件

同一サブタスクに対して実行中ジョブは常に最大1件とする。複数の追加指示は登録順に処理し、ワーカーのジョブ取得時にもこの条件を原子的に検査する。

外部GitHub操作とローカルDB更新の間で失敗が起き得るため、作成途中の状態とGitHubのIDを保持し、再試行時は既存ブランチ・PRの有無を確認して重複作成を避ける。

SQLiteファイル、レポート、worktree等の実行時生成物はGit管理対象から除外する。既存の継続利用データを削除するスキーマ変更は事前確認する。

GitHub操作は`gh` CLIをサブプロセスとして呼び出して行う：Issue取得（gh issue view）、ブランチ作成、PR作成・Draft（gh pr create --draft）、Draft解除（gh pr ready）、PRマージ状態取得（gh pr view）。認証は既存のgh OAuthセッションを使用する。

操作APIの保護

Cloudflare Accessの認証を前提とし、状態変更APIはサーバー側でも認証・認可とCSRF対策を実施する。ブラウザから渡されたリポジトリパス・コマンド・PR番号は信用せず、登録済み対象と照合する。

実行依頼の重複登録防止は画面の二重押下対策だけでなく、サーバー側の冪等性と同一サブタスク排他で担保する。

9. Claude Code実行ポリシー

確定 Claudeは原則質問せず、入力内容をもとに調査・合理的な判断・実装・テストを行う。自律判断した事項はHTMLに記録する。

あなたはClaude管理塔の自律実装ワーカーです。
対象：GitHub Issueと紐付く1サブタスク（1 PR）。
1. 指示、Issue、既存コード、プロジェクト規約を確認する。
2. 不明点は自ら調査し、合理的な前提を選んで作業を進める。
3. 原則としてユーザーへの問い合わせや応答待ちはしない。
4. 判断した事項と理由、残る不確実性を記録する。
5. 対象worktree・許可範囲で実装、テスト、修正する。
6. 変更内容・テスト結果・未解決課題を報告する。
7. 最終的に指定フォーマットのHTMLレポートを出力する。
8. 機密情報の公開、権限外操作、破壊的操作など安全に
   自律判断できない処理は実行せず、失敗理由を報告する。
9. Issueの自動クローズ、PRの自動マージは行わない。

実装提案 Web入力をそのままシェルに連結せず、構造化された引数としてClaude実行機構へ渡す。ClaudeのセッションIDは再実行時の継続に利用可能なら保持し、使えない場合は指示と履歴要約を渡す。

10. HTML作業報告書

確定 Claudeが自分で補足・判断した内容をHTMLでまとめる。管理塔で閲覧し、サブタスクの実行履歴として保存する。

必須項目（提案）

  1. 対象Issue・サブタスク・PR・ブランチ
  2. 実装結果の要約（成功／一部成功／失敗）
  3. 実施した変更と主な変更ファイル
  4. Claudeが自律判断した事項・採用理由・前提
  5. 実行したテストと結果（未実施なら理由）
  6. 残課題、リスク、レビュー時の確認ポイント
確定 Claude生成HTMLは信頼できない入力として扱い、厳格にsandbox化したiframeで隔離して表示する。MVPではHTMLサニタイズ方式との選択制にはしない。iframeには sandbox="" を指定し、allow-scripts と allow-same-origin は付与しない。レポート内の外部リソース読み込みはCSPで制限し、Webサーバーの認証トークンをHTMLに埋め込まない。

iframe表示の実装条件（確定方式の具体化）

レポートは専用のHTML応答として返し、管理画面ではsandbox=""付きiframeで表示する。allow-scripts、allow-same-origin、allow-top-navigation、allow-forms、allow-popups等の権限は付与しない。親画面のDOMへレポートHTMLを挿入しない。

レポート応答には制限的なContent-Security-Policyを設定し、スクリプト、外部接続、外部画像・フォント等の読み込みを原則禁止する。レポート内のリンク・フォーム・外部リソースは機能要件に含めない。

GitHubトークン、Cloudflare認証情報、Claude認証情報をレポートやログに書き込まない。機密情報のマスキングを行い、レポートファイルへの直接アクセスも認証の対象とする。

11. セキュリティ・運用

  • 外部アクセスはCloudflare Tunnel + Cloudflare Accessによる認証付きHTTPS。自宅ルーターのポート開放を前提にしない。
  • GitHub認証は`gh` CLIの既存OAuthセッション（Windows資格情報に保存）を使い回し、専用トークンを環境変数等に保持しない。Claude認証情報は環境変数・安全な秘密情報ストアで保持し、いずれもブラウザへ送らない。
  • 実行対象のリポジトリ・worktreeを許可リストで制限し、任意のOSコマンドをWebから直接実行させない。
  • Claude Codeは最小権限で実行し、危険な操作を無条件に許可しない。
  • ワーカーが異常終了した場合、DB上の実行中ジョブを「要確認」にしてログ・worktreeを点検する。自動二重実行はしない。
  • 自宅PCの電源・スリープ・ネットワーク切断中は遠隔操作不可。再起動後にサーバー・ワーカーを再起動できる運用を用意する。
  • 本プロジェクトのGitHubリポジトリは公開（Public）とする。自宅PCへの侵入につながる情報（実IPアドレス、Cloudflareトンネルの固有ホスト名・トークン、GitHub/Claude等の認証情報、ローカル環境固有のユーザー名を含むパス等）はコミット・push・Issue・PR・コメントのいずれにも記載しない。

実装提案 MVPは単一ユーザー・単一PC・Nワーカーを基本とする。複雑なRBAC、分散キュー、課金ダッシュボードは不要。

Claude実行とGit操作の境界

ワーカーには登録済みリポジトリと担当サブタスクのworktreeのみを割り当てる。別サブタスク・別ワーカーのworktreeを変更・削除しない。

共有ブランチへのforce push、hard reset、強制削除、秘密情報の送信、許可範囲外のファイル操作を自律実行しない。実行前の承認が必要な操作は安全側で停止し、理由を記録する。

ワーカー停止・PC再起動時にはheartbeatとプロセス生存を確認し、処理中だったジョブを要確認として扱う。重複実行を避けるため自動再投入はしない。

12. Claude Code向け実装順序と受け入れ条件

実装順序

  1. 環境検証：GitHub接続・Issue取得・差分なしブランチでDraft PR作成可否を確認。
  2. 基盤：FastAPI、SQLite、設定管理、Web画面、`gh` CLIラッパー。
  3. タスク画面：Issue一覧・詳細、サブタスク履歴、状態表示。
  4. Git連携：サブタスク作成 → ブランチ → Draft PR → GitHubリンク。
  5. ワーカー：独立プロセス、SQLiteジョブキュー、Claude実行、イベント保存。
  6. 成果物：コミット・push、HTMLレポート、Draft解除、PR同期。
  7. 遠隔操作：Cloudflare認証経由でスマホ表示・指示送信を確認。
  8. 並列実行：Nワーカー起動、原子的キュー取得、サブタスク別worktree、同一サブタスク排他、N=3での同時実行テスト。

受け入れチェックリスト

  • Issue一覧から対象Issueを選択できる。
  • 1 Issueに複数サブタスクを登録できる。
  • サブタスク作成時に専用ブランチとDraft PRを作成できる（環境検証に成功した場合）。
  • PR説明文が Related to #番号 であり、Issueを自動クローズしない。
  • Claudeの実装開始後にブラウザを閉じても処理が継続する。
  • Claudeの実行中・成功・失敗を管理塔で確認できる。
  • 指示、Claude応答、ログ、HTMLレポートが履歴として残る。
  • Claudeが判断した内容と理由をHTMLで確認できる。
  • Claude実装成功だけではサブタスクが完了にならない。
  • PRマージを同期すると該当サブタスクが完了になる。
  • 複数サブタスクが残っているIssueを最初のPRマージだけで閉じない。
  • スマホから認証付きで閲覧・指示できる。
  • N=3で異なる3件が並列実行され、4件目が待機して順次開始する。
  • 同一サブタスクの二重実行が起こらず、ワーカーごとの状態を確認できる。

13. Web技術の基礎（Web未経験のC#/.NETアプリ開発者向け）

補足説明 この章は実装要件ではなく、設計書を読み解き、Claude Codeが作成したプログラムを自分で理解するための説明。ASP.NET経験は前提にしない。

13.1 デスクトップアプリとの最大の違い

C#のデスクトップアプリでは、画面イベントから同一プロセスの処理を呼び出すことが多い。Webアプリでは、ブラウザ（画面）とサーバー（処理）が別のプロセスとして動き、HTTPという通信規約でやり取りする。スマホからでも操作できるのは、画面をブラウザが描画し、処理は自宅PCが担当するため。

【外出先スマホ】HTML/CSS/JavaScript（ブラウザ）
        │ HTTPリクエスト: POST /api/subtasks/123/execute
        ▼
【自宅PC】FastAPI（Webサーバー）
        │ SQLiteに実行依頼を登録 → すぐ受付結果を返す
        ▼
【自宅PC】Pythonワーカー（別プロセス）
        │ Claude Code起動・Git操作・ログ保存
        ▼
【自宅PC】SQLite / Git worktree

スマホはClaude実行の終了まで通信を開いたまま待つ必要がない。

13.2 それぞれの技術の役割

技術何を担当するか身近な例え
HTML画面の構造（見出し、ボタン、入力欄）画面の部品配置
CSS色・余白・スマホ対応などの見た目画面デザイン設定
JavaScriptクリック操作、API呼び出し、画面更新UIイベント処理

13.3 FastAPIの最小例

from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class RunRequest(BaseModel):
    instruction: str

@app.post("/api/subtasks/{subtask_id}/execute")
def execute(subtask_id: int, request: RunRequest):
    # 実際の実装ではここでSQLiteに実行依頼を登録する
    return {"accepted": True, "subtask_id": subtask_id}

@app.post(...) は指定URLへのPOST要求を関数へ対応付ける宣言。BaseModel は受信JSONを検証する。FastAPIは通常 http://127.0.0.1:8000/docs にAPIを試せる画面を提供する（公開環境では/docsのアクセスも制限する）。

13.4 ブラウザからAPIを呼ぶ例

const response = await fetch('/api/subtasks/123/execute', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ instruction: 'AIを実装して' })
});
const result = await response.json();

fetch はブラウザ標準の通信機能。POST は操作依頼、GET は情報取得に使う。レスポンスの accepted は「依頼を受け付けた」という意味であり、Claudeの実装完了ではない。

13.5 同期・非同期とワーカー分離

Claude実行は数分以上かかる可能性がある。HTTPリクエストの中でClaudeを直接実行して完了まで待つと、通信切断やタイムアウトに弱い。Webサーバーはキューに登録して即座に応答し、別プロセスのワーカーが後から処理する。画面は定期的に状態取得する（MVPは数秒ごとのポーリングで十分。WebSocketは後から追加可能）。

13.6 ブラウザとサーバーの責任分担

ブラウザに置くJavaScriptは利用者から読める。GitHubのアクセストークン、Claudeの認証情報、DBパスなどの秘密情報は必ず自宅PCのサーバー側に置く。ブラウザからの指示は信用せず、サーバー側で対象Issue・サブタスク・操作権限を検証する。

14. Windows PCでの構築・起動手順（実装提案）

実装提案 初回は自宅PC内だけで動作確認し、後から外部公開する。PowerShellの例を示す。実際のパスや起動コマンドはClaudeが生成するプロジェクトに合わせてREADMEへ記載する。

14.1 必要なもの

  • Windows PC、Python 3系、Git、Claude Code、GitHubアカウントと対象リポジトリ
  • Python仮想環境（venv）：プロジェクト固有のライブラリを分離する仕組み
  • `gh` CLIと`gh auth login`済みのGitHubセッション（専用トークンの発行は不要）

14.2 ローカル環境の起動例

py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt

# ターミナル1：Webサーバー
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000

# ターミナル2：別プロセスの実行ワーカー
python -m worker.main

上記の app.main と worker.main は推奨ディレクトリ構成の例で、実装時に一致させる。PowerShellの実行ポリシーによって仮想環境の有効化手順は異なる。初回は http://127.0.0.1:8000 から動作確認する。

14.3 推奨フォルダ構成

14.4 実装・検証を段階分けする

  1. FastAPIで固定データのタスク一覧を表示する。/docs からAPI呼び出しを試す。
  2. GitHub APIでIssue一覧を取得する。まず読み取り専用で確認する。
  3. SQLiteへサブタスクと実行依頼を保存し、ワーカーが取得できることを確認する。
  4. テスト用リポジトリでブランチ作成・Draft PR作成を検証する。差分ゼロのPR作成可否はGitHub環境に依存するため実環境で確認し、不可なら実装を止めて要件を相談する（自動フォールバックはMVP対象外）。
  5. Claude Code起動、実装ログ、HTML報告書、PR状態の同期を実装する。
  6. ローカルで完成後、Cloudflare TunnelとAccessを設定してスマホから確認する。

14.5 外部公開時の最低限の注意

FastAPIは原則 127.0.0.1 にバインドし、Cloudflare Tunnel経由で公開する。Cloudflare Accessの認証を設定し、可能ならアプリ側でもAccessのJWTを検証する。Web UIから任意のシェルコマンドや任意のファイルパスを指定できるようにはしない。状態変更APIには認証・権限確認・CSRF等の対策を適用する。

並列起動の補足：実装時には設定値 worker.count に従ってN個の独立したワーカープロセスを起動するランチャー（例：python -m worker.launcher）を用意する。単独起動コマンドはデバッグ用途とする。

16. MVP並列実行仕様（確定）

確定 MVP時点でワーカーN個・同時実行最大N件を達成する。Nは設定可能で、初期値は3（設定変更可能）。同一サブタスクの並列実行は禁止する。

16.1 処理構造

FastAPI Webサーバー（1プロセス）
      │ 指示登録 / 状態照会
      ▼
SQLite ジョブキュー（原子的なジョブ取得）
      ├── Worker 1 → Claude Code 1 → worktree A
      ├── Worker 2 → Claude Code 2 → worktree B
      ├── Worker 3 → Claude Code 3 → worktree C
      └── ... Worker N → Claude Code N → worktree N

16.2 ワーカー制御

  • ワーカー1個は同時に1ジョブだけ実行し、終了後に次のジョブを取得する。
  • キューからのジョブ取得はSQLiteの短い書き込みトランザクション内で「待機中→実行中」を原子的に更新する。
  • 同一サブタスクのジョブは同時に実行しない。追加指示はキューに入れて順番に処理する。
  • サブタスクごとに専用worktreeを用意する。異なるサブタスクが同一リポジトリに属していても編集領域は分離する。
  • Gitの共有メタデータに影響するworktree作成・削除などは、リポジトリ単位で短時間の排他制御を行う。
  • 1件のClaude実行が失敗しても他ワーカーは継続する。ワーカー異常終了後のジョブは要確認とし、無条件の自動二重実行はしない。
  • 並列worktreeでもPR間の論理的な依存やマージ競合は起こり得る。依存PRは前提PRのマージ後に実行するか、実行前に依存関係を明示する。

16.3 設定例（実装提案）

worker:
  count: 3
  max_concurrent_tasks: 3
  polling_interval_seconds: 3
execution:
  worktree_per_subtask: true
  allow_same_subtask_parallel: false

初期MVPでは count と max_concurrent_tasks を同じ値にする。Web画面の状態更新は従来どおり3秒程度のポーリングでよい。ワーカー数を増やす際はPCリソースとClaudeの利用制限を考慮する。

16.4 受け入れ条件

  • N=3で異なる3件のサブタスクが同時にClaude Codeを実行する。
  • 4件目は待機し、ワーカーが空くと自動的に開始する。
  • 同一サブタスクへの複数指示は同時実行されず、順番に処理される。
  • 同じGitリポジトリの3件を別々のworktreeで実行できる。
  • 1件が失敗しても他の実行は継続する。
  • 管理画面とスマホでワーカーの稼働状態と担当ジョブを確認できる。
  • Nを設定変更して起動すると、起動ワーカー数と同時実行上限が変わる。

並列実行の追加受け入れ条件

異なるサブタスクを同一リポジトリで同時実行しても、worktreeの編集対象が交差しないこと。worktreeの作成・削除など共有Gitメタデータの変更時のみ短時間の排他を行うこと。

同じサブタスクに追加指示を連続登録した場合、実行中ジョブと次の待機ジョブが同時に起動しないこと。

ワーカーの強制終了後、該当ジョブが自動的に別ワーカーで二重実行されず、要確認状態として管理画面に表示されること。
