1. 目的とスコープ

現在のClaude管理塔は、人間がGitHub Issueを起票し、Claudeがサブタスク単位で実装する構成になっている。\ アイデアマンは、この起点を補う役割として、既存コード・過去の実行履歴をClaude自身が調査し、改善提案（Issueの種・サブタスク/MRの種）を見つける機能を指す。

基本思想：「Claudeが自分でコード・運用履歴を観察 → 改善案を提案 → 人間が確認・承認 → 既存の起票・実装パイプラインに乗せる」。アイデアマン自身はIssue・PRを即時には作らず、提案までを担当する。

MVPに含む

  • 対象リポジトリのソースコード・ドキュメントの調査
  • 過去の実行履歴（execution_events・reports・失敗ジョブ）の調査
  • 既存Open Issueとの重複チェック
  • 調査結果をもとにしたIssue案・サブタスク案の提案、人間承認を経たGitHubへの反映

MVPから除外

  • ブラウザ操作による実際のUI動作確認（動的テスト）
  • 人間の承認を経ないGitHub Issue・PRの自動作成
  • 定期実行（スケジューラ）。初期は手動トリガーのみ

2. 既存システムとの関係

新規提案 アイデアマンは独立した新システムではなく、既存のワーカープール・ジョブキューに相乗りする新しいジョブ種別として実装する。Claude Agent SDK・worktree・ジョブキューといった既存の実行基盤を再利用し、実装を複雑化させない。

既存ワーカープール（WorkerPool）
  ├─ 実行ジョブ（サブタスク実装） … 既存
  └─ アイデア出しジョブ（idea_generation） … 新規
       │ 対象リポジトリを読み取り専用で調査
       │ 過去のexecution_events・reports・Open Issueも参照
       ▼
     ideas テーブルへ提案を保存（GitHubへはまだ何も書かない）
       │ 人間が画面で確認し、承認 or 却下
       ▼
  承認時のみ、既存の「サブタスク作成」「Issue作成」相当のAPIを呼び出す

アイデアマンのジョブは原則としてコミット・push・GitHub書き込みAPIを呼ばない。\ 既存のcan_use_toolによるworktree外操作の拒否機構はそのまま適用し、読み取り専用である点を実行ポリシー（7章）でも明示する。

3. 分析対象（インプット）

分類内容用途
静的ソースコード全体（app/core/worker/tests）設計の歪み・重複・未使用コード・肥大化した関数の発見
静的README・CLAUDE.md・IMPLEMENTATION_PLAN.md既存方針との整合確認、方針違反の提案を避ける
動的execution_events・reports過去のClaudeの自律判断・残課題の傾向からの改善点抽出
動的失敗ジョブ・needs_attentionの履歴繰り返し発生している不具合・弱点の特定
GitHubOpen Issue一覧重複提案の回避
GitHub直近のPRレビューコメント人間が繰り返し指摘している観点の特定
MVP除外とする項目：ブラウザでの実際のUI操作・画面確認（動的テスト）はMVPから除外する。\ claude-in-chrome等のブラウザ操作手段自体は利用可能だが、人間が実際にClaude管理塔を使用中の場合に操作が競合するリスクがあり、対応は後続フェーズの検討事項とする（10章・No.4）。

4. 提案データモデル

新規提案 1件の提案をideasとして保存する。GitHubのIssue・PRそのものではなく、アプリ内の保留データとして扱う。

ideas
  id, project_id, source_job_id,
  category(bug|feature|refactor|tech_debt|docs),
  title, summary, detail, rationale, related_files,
  related_issue_number NULL,
  status(proposed|approved_issue_only|approved_with_subtask|rejected|issue_created|subtask_created),
  created_issue_number NULL, created_subtask_id NULL,
  created_at, decided_at NULL

related_issue_numberは、既存Open Issueの改善案（新規Issueを作らず既存Issue配下にサブタスクを追加する提案）の場合に設定する。\ rationaleには対象ファイル・行・観測した事象など、人間が承認判断をする際の根拠を記録する。

5. 承認フロー（安全策）

既存リスクとの関係：IMPLEMENTATION_PLAN.md 8章で「Issue作成にはPRのDraftに相当する保留状態がなく、作成した瞬間に公開リポジトリへ即時反映される」という残存リスクが既に指摘されている。\ アイデアマンがIssue作成の起点を増やすことで、このリスクが拡大する可能性がある。\ そのため提案は必ずアプリ内の保留状態（ideasテーブル）に留め、人間の承認を経てから初めてGitHub Issueを作成する。

一方、サブタスク・Draft PRの作成はGitHub側に既に「Draft」という保留状態があり、マージせずにクローズすれば実質的に取り消せる。\ そのためアイデアマンの承認モデルは、提案の対象がIssueかサブタスク/PRかで扱いを分ける案とする。

提案の対象承認の要否根拠
新規Issue提案人間の承認が必須Issue作成は取り消せない残存リスクが既にある（IMPLEMENTATION_PLAN.md 8章）
既存Issue配下の新規サブタスク/PR提案初期運用では人間の承認が必須。実績を見て緩和を検討Draft PRは安全に保留できるが、自己起票での自律実行の実績がまだないため初期は承認制にする

承認操作では、人間は提案を「Issueのみ作成」「Issue作成＋初回サブタスク（実装着手）も作成」「却下」のいずれかから選ぶ。\ 「Issue作成＋初回サブタスクも作成」を選んだ場合、既存のサブタスク作成パイプライン（ブランチ作成→初期コミット→Draft PR作成→実行ジョブ投入）をそのまま呼び出す。

6. 実行トリガーと画面仕様

新規提案 画面に対象プロジェクトごとの「アイデア出し実行」ボタンを設け、手動トリガーでアイデア出しジョブを投入する。\ 実行中は既存ジョブと同様にワーカー1個を占有し、稼働状況パネルに表示する。

提案一覧パネル

新規パネル「提案一覧（アイデアマン）」を設け、ステータス別（未処理／承認済み／却下済み）にタブ分けする。\ 提案カードには、タイトル・カテゴリ・根拠・関連ファイル・対象Issue（既存Issue配下の場合）を表示し、「Issueを作成」「サブタスクも作成」「却下」の操作を置く。

スマホでは縦積み表示とし、既存の画面構成（上部一覧・下部詳細）と同じ操作感に合わせる。

7. Claude実行ポリシー

新規提案 既存の実行ポリシー（設計書9章）に準じつつ、読み取り専用である点を明示したプロンプトとする。

あなたはClaude管理塔のアイデアマンです。
対象：指定リポジトリのコード・ドキュメント・過去の実行履歴。
1. コードの変更・コミット・push・GitHubへの書き込み操作は行わない（読み取り専用）。
2. 既存のOpen Issue一覧を確認し、重複する提案は作らない。
3. 1回の実行で提案する件数は最大{N}件とする。
4. 各提案には、対象ファイル・行・観測した事象など根拠を明記する。
5. 機密情報・個人情報を提案の本文に記載しない。
6. 提案はあくまで案であり、Issue・PRの作成はこのジョブの中では行わない。

対象worktreeは既存の割り当て機構を再利用するが、書き込み権限を持たせない読み取り専用の割り当てとする。\ 既存のcan_use_toolコールバックで、このジョブ種別に限りファイル変更・Git書き込み操作を拒否する。

8. データモデル・API追加案

MethodEndpoint用途
POST/api/projects/{id}/ideas/runアイデア出しジョブを投入
GET/api/projects/{id}/ideas提案一覧取得（ステータス別）
POST/api/ideas/{id}/approve承認（Issueのみ／サブタスクも作成）
POST/api/ideas/{id}/reject却下（理由を記録）

承認時のIssue作成・サブタスク作成は、既存の/api/subtasks相当の処理をそのまま内部呼び出しする。\ 新しいGitHub操作コードを追加しない方針とする。

新規実装・未検証の変更は、既存方針（CLAUDE.md）に従いclaude-tower-test-repoで検証してから本体に適用する。
