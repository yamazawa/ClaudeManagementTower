2. 実装結果の要約

成功

  • 提案一覧ダイアログの見出し行の下に、観点の入力欄（任意・1000文字まで）を追加した。
  • 入力した観点はアイデア出しジョブ（idea_jobs.focus）に保存し、ワーカーへ渡す。
  • 観点の指定があれば、Claudeへの指示文の調査依頼の直後に「重視する観点」の節を含める。
  • ダイアログを開いた直後は、前回のアイデア出しの観点で入力欄を埋める。
  • 実行中は入力欄を無効化する。

4. 自律判断した事項・採用理由・前提

No.判断理由・前提
1観点は自由記述の1項目とした（選択式にしない）指示が「どういう観点で」と自由度の高い要望のため。選択肢は運用を見て追加できる
2観点はジョブ単位で保存し、提案単位には持たせないワーカーがDBからジョブを取得する構成のため、ジョブに保存するのが最小の変更になる
3既存DBへは起動時に列を追加する（ALTER TABLE ... ADD COLUMN）DBはcreate_allのみで列追加されず、そのままでは稼働中の管理塔がidea_jobs参照時に失敗するため。ガイドラインの「移行コードを書かない」と衝突するが、実装計画3章No.3の運用開始後ルール（既存データを消さない）を優先し、9章No.19に記録した
4観点の上限を1000文字とした指示文の肥大化を防ぐため。画面のmaxlengthとAPIの検証（超過は422）を合わせた
5観点に合う提案が無ければ件数を埋めない旨を指示文に含めた観点外の提案で件数を埋めると、指定の意味が薄れるため
6前回の観点で入力欄を初期表示する同じ観点での再実行を想定。不要なら消して実行すればよい
7リクエスト本文は省略可とした既存の呼び出し（本文なし・{}）との互換のため

6. 残課題・リスク・レビュー時の確認ポイント

  • 画面での見た目（入力欄の位置・スマホ幅での表示）を確認してほしい。
  • 既存DBへの列追加は、管理塔の再起動時（init_db実行時）に行われる。再起動前に新しいワーカーが動くとfocus列が無く失敗する可能性がある。
  • ADDED_COLUMNSの仕組みを今後のスキーマ変更にも使うか、今回限りとするかの判断が必要。
  • 観点は提案カードには表示していない。どの観点で出た提案かを表示したい場合は後続で対応する。
  • 入力欄のプレースホルダーに入力例を入れている。不要であれば削除する。
