4. 自律判断した事項

No.判断理由・前提
1取り消し順をworktree→ローカルブランチ→リモートブランチとし、厳密な逆順にしないgit branch -dは上流ブランチで取り込み済みかを判定する。先にリモートを消すと追跡ブランチが消え、-dが拒否されるため。
2--force・-Dは使わない3章No.2の方針に従う。
3push前の失敗では、指示コミットを持つローカルブランチが残る未pushコミットは-dで削除できないため。残存物としてエラーメッセージで報告する。
4worktree削除前に.venvジャンクションをcmd /c rmdirで外す削除処理がジャンクション先の本体の仮想環境を辿って消す事故を防ぐため。
5コミット前に失敗した場合、自分が作った指示ファイルだけをgit rm --cachedと削除で取り除く強制なしのgit worktree removeが、未コミット変更で拒否されるのを避けるため。
6リモートブランチの削除はpush成功時のみ行うpush失敗時はリモートに無い前提とした。
7後始末後は元の例外型でメッセージを付け直して投げ直す呼び出し側のHTTP 500変換をそのまま使えるため。
8後始末処理は新規モジュールcore/subtask_rollback.pyに分離routesファイルの肥大化を避け、1クラス1責務に寄せるため。

6. 残課題・リスク・レビュー観点

  • push前の失敗では、ローカルブランチが残る。同じ連番での再作成はブランチ名重複で失敗する。
  • pushがタイムアウトしたがリモートには反映済み、というケースではリモートブランチが残る。
  • Draft PR作成がタイムアウトしたがPRは作成済み、というケースでは、PRのブランチを削除してしまう可能性がある（PRはクローズ扱いになる）。
  • Draft PR作成後のDB保存失敗は取り消さない（自動同期で管理塔外PRとして取り込まれる）。
  • レビュー観点：取り消し順の妥当性、git branch -dのみで足りるか、エラーメッセージの文言。
